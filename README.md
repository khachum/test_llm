# Отчёт: инференс Qwen3-8B и Qwen3-32B на 4 × Ascend 910B1 под vLLM-Ascend

Работа выполнена по методике тестирования ИИ-ускорителей Ascend 910B (учебная версия; в репозиторий не входит) на арендованном инстансе
hitee ai. Дата: **18–19.09.2026**. Движок — vLLM-Ascend 0.23.0.

Материалы: [`Qwen3-8B/`](Qwen3-8B/) и [`Qwen3-32B/`](Qwen3-32B/) — отчёты по моделям, команды запуска,
логи серверов и бенчмарков, телеметрия; [`results/results.csv`](results/results.csv) — все прогоны
одной таблицей; [`scripts/`](scripts/) — скрипты развёртывания, оркестрации и обработки.

## 1. Главное

1. **Образ провайдера был нерабочим для этих карт.** В поставленном CANN лежали ядра операторов под
   чип 310p, а под 910B — только служебный набор. Любая операция на NPU падала с
   `Parse dynamic kernel config fail`. Пришлось ставить свой CANN 9.1.0 в `/data`. Тот же дефект,
   но с другим чужим чипом, встречался на другом инстансе того же провайдера 15.09.2026 — это
   системная особенность, а не разовый сбой.
2. **Для Qwen3-8B выгоднее всего одна карта на реплику.** Тензорный параллелизм на модели такого
   размера даёт S(2) = 0.64–0.76 и S(4) = 0.37–0.47, то есть четыре карты работают как полторы-две.
   Смысл TP здесь — только снижение задержки одиночного запроса.
3. **Qwen3-32B на двух картах держит интерактивный режим лишь до 16 запросов, на четырёх — до 64.**
   При этом масштабируется она хорошо (S = 0.79–0.81 при удвоении карт), в отличие от 8B: выгодность
   тензорного параллелизма прямо зависит от размера модели.
4. **Энергоэффективность растёт с параллельностью и падает с числом карт.** Пик серии —
   10.93 токена на джоуль (8B, одна карта, 64 запроса).
5. Утилизация AI-ядер не превышала 71 % ни в одном прогоне: узкое место — не вычислители, а
   пропускная способность памяти и планировщик.

15.06.2026. Поэтому «взять версию посвежее» здесь означает откатить vLLM, а не обновить его.

Все шаги оформлены идемпотентными скриптами в [`scripts/`](scripts/), на стенде они лежат в

Порядок воспроизведения на чистом инстансе — раздел 9.

### Журнал развёртывания

**Ж1. В образе стенда CANN с ядрами операторов под чужой чип.**
Симптом: `torch.npu.is_available()` истинно, карт видно 4, но любая операция падает:

```
RuntimeError: call aclnnMatmul failed, error code is 561103
[ERROR] OP ... [kernel_mgr.cpp:223] Parse dynamic kernel config fail.
```

Диагноз — в `/usr/local/Ascend/cann-9.1.0-beta.1` ядра только под 310p:

```
4.2G  .../kernel/ascend310p     ← ops_cv, ops_math, ops_nn, ops_transformer
5.4M  .../kernel/ascend910b     ← только ops_oam
```

Поиск по всей файловой системе другого комплекта ядер не дал ничего, все `set_env.sh` ведут в ту же
установку. Обход: свой CANN 9.1.0 в `/data/Ascend`, работа только через `source env.sh`.

**Ж2. Ловушка `pkill -f` в SSH-сессии.** Команда `ssh host 'pkill -f install_cann.sh'` убивает сама
себя: шаблон входит в командную строку удалённого `bash -c`. Дважды оборвало сессию, один раз оставило
установщик работать сиротой. Правильно: шаблон вида `[i]nstall_cann.sh`, исключение `$$`, а скрипты с
такими строками заливать файлом через stdin.

**Ж3. Зеркала Ascend-пакетов рвут соединение.** `pip install vllm-ascend==0.23.0` тянет
`triton-ascend` с `mirrors.huaweicloud.com` со скоростью ~270 КБ/с и обрывами; pip не умеет
докачивать и после шести попыток откатывает **всю** установку целиком — из-за чего в venv не
оказалось ни `vllm-ascend`, ни `torch_npu`, а `torch` остался версии 2.11.0. Обход: скачать wheel
отдельно через `wget -c` (докачивает с места обрыва) и поставить из локального файла.

**Ж4. Конфликт numpy между компонентами.** После установки `pandas`/`matplotlib` движок падал на
старте: `ImportError: Numba needs NumPy 2.4 or less. Got NumPy 2.5`. При этом `triton-ascend 3.2.2`
требует ровно `numpy==1.26.4` и `scipy==1.13.1`. Рабочая комбинация — понизить обе библиотеки до этих
версий; она же стояла на стенде от 15.09.2026. Предупреждения `pip` о несовместимости с `ml-dtypes`,
`contourpy` и `opencv-python-headless` при этом остаются, но на инференс не влияют.

**Ж5. Безвредные сообщения.** `Failed to import Triton kernels ... constexpr_function` при каждом
старте сервера — это попытка загрузить CUDA-ядра Triton, на NPU они не нужны. Также безвредны
`LD_PRELOAD detected` и `Capturing CUDA graphs` (на Ascend это ACL-графы, название осталось от CUDA).

## 4. Методика замеров

Нагрузка подаётся `vllm bench serve` на синтетическом датасете `random` с `--ignore-eos`, seed 1234.
Профили длин по методике:

| Код | input → output | Что моделирует |
|---|---|---|
| P1 | 512 → 512 | симметричный чат |
| P2 | 2048 → 128 | извлечение факта из текста, prefill-нагрузка |
| P3 | 256 → 1024 | генерация по краткому заданию, decode-нагрузка |

Уровни параллельности: **1 / 16 / 64**. Первый прогон каждой конфигурации — разогревочный и в таблицу
не входит. Телеметрия снимается параллельно каждому прогону с частотой 0.5 Гц и агрегируется по
активным картам (тем, где загружены веса).

Отступления от методики и их причины:

| Пункт методики | Что сделано | Почему |
|---|---|---|
| Два движка (vLLM + SGLang) | только vLLM-Ascend | заказана быстрая серия; SGLang не разворачивался |
| Базовая модель Qwen3-14B | Qwen3-8B и Qwen3-32B | выбор заказчика работы |
| `num_prompts` = 10 × concurrency, не менее 100 | 6 / 48 / 128 для conc 1 / 16 / 64 | «быстрые» прогоны; фактическое число записано в каждой строке CSV |
| Кривая до concurrency 64 | сохранена | но для четырёх карт этого мало, см. раздел 8 |
| Профили P4, P5 | не снимались | `--max-model-len` = 8192 |
| Каждый прогон дважды | по одному разу | не хватило машинного времени; разброс не оценён |
| Свой датасет из 200 живых запросов | не собирался | вне рамок быстрой серии |

## 5. Результаты: Qwen3-8B (bf16)

Подробный разбор — [`Qwen3-8B/README.md`](Qwen3-8B/README.md). Веса 16 ГБ, помещаются на одну карту,
KV-кэш при TP=1 — 39.3 ГБ (286 464 токена).

Профиль P1, выходных токенов в секунду:

| конфигурация | карт | conc=1 | conc=16 | conc=64 | на карту при 64 | ток/Дж при 64 |
|---|---|---|---|---|---|---|
| tp1 | 1 | 60.3 | 789.8 | 1969.7 | **1969.7** | **10.93** |
| tp2 | 2 | 91.3 | 1110.9 | 2507.5 | 1253.8 | 8.65 |
| tp4 | 4 | 89.4 | 1269.8 | **3670.9** | 917.7 | 7.20 |
| dp2 | 2 | 66.3 | 912.9 | 2644.0 | 1322.0 | 7.64 |
| dp4 | 4 | 66.0 | 935.8 | 2987.7 | 746.9 | 4.81 |

Эффективность масштабирования S(n) = throughput(n) / (n × throughput(1)):

| | conc=1 | conc=16 | conc=64 |
|---|---|---|---|
| S(2) | 0.76 | 0.70 | 0.64 |
| S(4) | 0.37 | 0.40 | 0.47 |

Точка насыщения (TTFT ≤ 2 с и TPOT ≤ 50 мс): на P1 и P3 не достигнута даже при 64 запросах;
на P2 равна 16 — при 64 TPOT вырастает до 57.5 мс.

## 6. Результаты: Qwen3-32B (bf16)

Подробный разбор — [`Qwen3-32B/README.md`](Qwen3-32B/README.md). Веса 62 ГБ, на одну карту не
помещаются, минимальная конфигурация — TP=2 (31 ГБ на карту), KV-кэш 193 408 токенов.

Профиль P1, выходных токенов в секунду:

| конфигурация | карт | conc=1 | conc=16 | conc=64 | на карту при 64 | ток/Дж при 64 |
|---|---|---|---|---|---|---|
| tp2 | 2 | 30.6 | 383.2 | 986.0 | **493.0** | **2.38** |
| tp4 | 4 | 48.1 | 609.2 | **1594.2** | 398.6 | 2.28 |
| dp2tp2 | 4 | 30.6 | 423.0 | 1259.2 | 314.8 | 1.66 |

Профили P2 и P3 снимались на `tp2`. Самый тяжёлый режим — P2 (2048→128): 319.6 ток/с при 64 запросах
против 1115.9 на P3.

Эффективность масштабирования, база — минимальный работающий TP=2:

| | conc=1 | conc=16 | conc=64 |
|---|---|---|---|
| S при tp2 → tp4 | 0.79 | 0.79 | 0.81 |

Точки насыщения (TTFT ≤ 2 с, TPOT ≤ 50 мс):

| конфигурация | P1 | P2 | P3 |
|---|---|---|---|
| tp2 (2 карты) | 16 | не достигнута даже при 1 | 16 |
| tp4 (4 карты) | ≥ 64 | — | — |
| dp2tp2 (4 карты) | ≥ 64 | — | — |

## 7. Сравнение моделей

| | Qwen3-8B | Qwen3-32B |
|---|---|---|
| Веса | 16 ГБ | 62 ГБ |
| Минимум карт | 1 | 2 |
| TPOT при conc=1 | 15.0 мс | 32.5 мс |
| Скорость для одного пользователя | 66 ток/с | 31 ток/с (48 на четырёх картах) |
| Throughput при conc=16, 2 карты | 1110.9 | 383.2 |
| Throughput при conc=64, 4 карты | 3670.9 | 1594.2 |
| Точка насыщения по P1 | ≥ 64 на одной карте | 16 на двух картах, ≥ 64 на четырёх |
| Эффективность масштабирования | S(2) = 0.64–0.76, S(4) = 0.37–0.47 | S(tp2→tp4) = 0.79–0.81 |
| Пик утилизации AI-ядер | 71 % | 76.6 % |
| Энергоэффективность, лучшая | 10.93 ток/Дж (1 карта) | 2.38 ток/Дж (2 карты) |

Два вывода из сравнения:

1. **Отношение производительности близко к обратному отношению весов.** При равном железе (две карты,
   P1, 16 запросов) 32B выдаёт в 2.9 раза меньше токенов в секунду и требует вдвое большего времени
   на токен; энергоэффективность падает в 4.6 раза при росте весов в 3.9 раза. На стадии decode время
   определяется чтением весов из HBM, поэтому такая пропорция ожидаема.
2. **Выгодность тензорного параллелизма прямо зависит от размера модели.** У 8B четыре карты работают
   как полторы-две (S(4) = 0.37–0.47), у 32B удвоение карт даёт S = 0.79–0.81. Чем «толще» слои,
   тем лучше обмен активациями перекрывается вычислениями. Отсюда практическое правило для этого
   стенда: **мелкую модель размножать репликами, крупную — резать тензорно**.

## 8. Выводы о пригодности стенда

1. **Для моделей до ~10B этот ускоритель хорош в режиме «одна карта — одна реплика».** Одна карта
   держит 64 одновременных запроса в чатовом профиле, не выходя за интерактивные пределы, и даёт
   лучшую энергоэффективность.
2. **Цена тензорного параллелизма зависит от размера модели.** Для 8B S(4) = 0.37–0.47: три четверти
   добавленных карт уходят в коммуникацию. Для 32B удвоение карт даёт S = 0.79–0.81 — приемлемо.
   Правило для этого стенда: мелкие модели размножать репликами, крупные резать тензорно.
3. **Для 32B рабочий минимум — четыре карты.** На двух модель запускается, но интерактивный режим
   держится лишь до 16 запросов, а на длинном prefill не держится вовсе. Четыре карты поднимают
   предел до 64 запросов и снижают TPOT с 59 до 37 мс.
4. **Профиль с длинным prefill — самый тяжёлый.** На нём первыми деградируют и TPOT, и хвосты TTFT,
   у обеих моделей.
5. **Карта не загружается полностью:** максимум 71 % утилизации AI-ядер. Это говорит о запасе по
   вычислениям и об упоре в память и планировщик — направление для дальнейшей настройки.

## 9. Воспроизведение на чистом инстансе

```bash
# 1. CANN 9.1.0 в /data (около 15 минут, 4.3 ГБ загрузки)
bash scripts/install_cann.sh                 # → /data/Ascend

# 2. venv с движком (около 25 минут)
bash scripts/install_vllm.sh                 # → /data/venv-vllm
#    если оборвётся на triton-ascend:
bash scripts/fix_install.sh                  # wget -c + установка из файла

# 3. окружение и смоук-тест
source /data/scripts/env.sh
python -c "import torch, torch_npu; x=torch.randn(1024,1024).npu(); print((x@x).sum())"

# 4. веса с ModelScope (16 и 62 ГБ, десятки минут)
modelscope download --model Qwen/Qwen3-8B  --local_dir /data/models/Qwen3-8B
modelscope download --model Qwen/Qwen3-32B --local_dir /data/models/Qwen3-32B

# 5. серии замеров
python /data/scripts/run_suite.py /data/scripts/plan_8b.json
python /data/scripts/run_suite.py /data/scripts/plan_32b.json

# 6. обработка (локально)
python scripts/recompute_telemetry.py results/results.csv .
python scripts/make_report.py results/results.csv .
```

Ожидаемое время полного цикла — около 4 часов, из них примерно 2.5 часа машинного времени карт.

## 10. Что осталось недоснятым

- **concurrency 128 и 256.** Без них точка насыщения для 8B не найдена, а сравнение TP и DP неполно:
  при потолке в 64 запроса каждая из четырёх реплик DP получает лишь по 16 и работает вполсилы.
- **Повторные прогоны.** Методика требует двух прогонов каждой точки с указанием разброса; снят один,
  поэтому разброс неизвестен и числа следует считать оценкой.
- **Профили P4 и P5** (8192→512 и 32768→1024): требуют `--max-model-len` от 16k и длительных прогонов.
- **Второй движок (SGLang).** Сравнение двух движков — отдельный пункт методики, он не выполнялся.
- **Топология карт.** `npu-smi info -t topo` не снималась, поэтому объяснение просадки S(4) через
  разные корневые комплексы остаётся гипотезой, подкреплённой только Bus-Id.
- **Живой датасет** из 200 запросов на русском для сравнения с синтетикой.
